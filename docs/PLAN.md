# برنامه اجرای MVP

این برنامه مرحله‌ای است. هر مورد پس از انجام و گذراندن آزمون مربوط، علامت زده می‌شود. دروازه‌های تأیید کاربر باید پیش از ورود به مرحله بعد رعایت شوند.

## بخش اول: برنامه‌ریزی و تأیید

- [ ] ساختار فعلی پروژه و فرانت‌اند موجود را بررسی و محدودیت‌ها و وابستگی‌های آن را ثبت کن.
  - آزمون/معیار موفقیت: مسیرهای موجود و روش اجرای فرانت‌اند مشخص شده باشد؛ فایل‌ها در این مرحله تغییر نکنند.
- [ ] این برنامه را با گام‌های اجرایی، آزمون‌ها و معیارهای موفقیت کامل کن.
  - آزمون/معیار موفقیت: تمام قابلیت‌های MVP و تصمیم‌های ثبت‌شده در گفت‌وگو در این سند پوشش داده شوند.
- [ ] فایل `frontend/AGENTS.md` را برای توضیح ساختار و الگوهای کد فرانت‌اند ایجاد کن.
  - آزمون/معیار موفقیت: فایل ایجاد شده و راهنمای آن با فایل‌ها و ابزارهای واقعی فرانت‌اند مطابقت داشته باشد.
- [ ] طرح و برنامه را برای بررسی کاربر ارائه کن و پیش از ادامه تأیید بگیر.
  - آزمون/معیار موفقیت: تأیید صریح کاربر ثبت شده باشد.

## بخش دوم: آماده‌سازی ساختار اولیه پروژه

- [x] Docker را طوری پیکربندی کن که فرانت‌اند و بک‌اند در یک کانتینر اجرا شوند.
  - آزمون/معیار موفقیت: ساخت تصویر Docker موفق باشد و کانتینر بدون خطا بالا بیاید.
- [x] بک‌اند FastAPI را در `backend/` ایجاد کن و مدیریت وابستگی‌های Python در کانتینر را با `uv` انجام بده.
  - آزمون/معیار موفقیت: برنامه FastAPI اجرا شود و نقطه پایانی ساده API پاسخ موفق بدهد.
- [x] ارائه فایل‌های استاتیک فرانت‌اند را از مسیر اصلی `/` پیکربندی کن و یک صفحه HTML ایستای Hello World بساز.
  - آزمون/معیار موفقیت: بازکردن `/` در مرورگر صفحه را نشان دهد و درخواست API از همان سرویس پاسخ معتبر بگیرد.
- [x] اسکریپت‌های راه‌اندازی و توقف را در `scripts/` برای Mac، Windows و Linux اضافه کن.
  - آزمون/معیار موفقیت: هر جفت اسکریپت، سرویس را راه‌اندازی و متوقف کند؛ رفتار و پیش‌نیازها در خود اسکریپت‌ها روشن باشد.

## بخش سوم: ارائه فرانت‌اند کانبان

- [x] Next.js را برای ساخت استاتیک آماده کن و خروجی را از FastAPI در مسیر `/` ارائه بده.
  - آزمون/معیار موفقیت: ساخت فرانت‌اند و ارائه خروجی از کانتینر موفق باشد؛ صفحه اصلی در `/` بارگذاری شود.
- [x] برد نمایشی را با ستون‌های «برای انجام»، «در حال انجام»، «انجام‌شده»، «در انتظار تأیید»، «پروژه‌های در انتظار» و «پروژه‌های اتمام‌شده» نمایش بده.
  - آزمون/معیار موفقیت: هر شش ستون در برد دیده شوند و محتوای نمایشی موجود باشد.
- [x] امکان تغییر نام ستون‌ها، جابه‌جایی ترتیب ستون‌ها با کشیدن سربرگ، ویرایش کارت‌ها و جابه‌جایی کارت‌ها با کشیدن و رهاکردن را فراهم کن.
  - آزمون/معیار موفقیت: آزمون رابط کاربری تغییر نام و بسته‌شدن فرم با Enter، تغییر ترتیب ستون بدون جابه‌جایی کارت‌ها، ویرایش و انتقال کارت به ستون دیگر را تأیید کند.
- [x] آزمون‌های واحد، یکپارچه‌سازی و مرورگر را برای رفتارهای فرانت‌اند اضافه کن.
  - آزمون/معیار موفقیت: آزمون‌ها اجرا شوند و نمایش برد و تعامل‌های بالا را پوشش دهند.

## بخش چهارم: ورود آزمایشی کاربر

- [x] ورود با نام کاربری `user` و رمز عبور `password` را پیش از نمایش برد الزامی کن.
  - آزمون/معیار موفقیت: اعتبارنامه صحیح دسترسی بدهد؛ اعتبارنامه نادرست دسترسی ندهد و پیام خطا نمایش داده شود.
- [x] نشست ورود را در همان تب تا خروج صریح یا بسته‌شدن تب حفظ کن و امکان خروج را اضافه کن.
  - آزمون/معیار موفقیت: بارگذاری مجدد در همان تب ورود را حفظ کند؛ خروج یا بسته‌شدن تب دسترسی به برد را ببندد.
- [x] مسیرهای مستقیم و حالت‌های ورود/خروج را در آزمون‌های رابط کاربری پوشش بده.
  - آزمون/معیار موفقیت: کاربر بدون ورود نتواند برد را مشاهده کند و پس از خروج به صفحه ورود برگردد.

## بخش پنجم: مدل‌سازی پایگاه داده

- [x] طرح SQLite را در یک فایل JSON تعریف کن؛ مدل داده باید از چند کاربر پشتیبانی کند و برای هر کاربر یک برد در نظر بگیرد.
  - آزمون/معیار موفقیت: فایل JSON معتبر باشد و رابطه کاربر، برد، ستون و کارت را همراه با محدودیت‌های لازم مشخص کند.
- [x] ستون‌های آغازین برد و تغییر نام آن‌ها را در طرح داده پوشش بده.
  - آزمون/معیار موفقیت: طرح، شش ستون تعیین‌شده را قابل ذخیره و نام ستون را قابل تغییر کند.
- [x] روش و دلیل انتخاب مدل داده را در مستندات `docs/` توضیح بده و طرح را برای تأیید به کاربر ارائه کن.
  - آزمون/معیار موفقیت: مستندات با فایل JSON سازگار باشند و پیش از پیاده‌سازی پایگاه داده تأیید صریح کاربر دریافت شود.

## بخش ششم: بک‌اند و API

- [x] مدل‌ها و مسیرهای API را برای خواندن و تغییر برد، ستون‌ها و کارت‌ها پیاده‌سازی کن.
  - آزمون/معیار موفقیت: درخواست‌های API داده معتبر برگردانند و تغییرهای مجاز را ذخیره کنند.
- [x] هنگام نبودن فایل SQLite، پایگاه داده و ساختار لازم را به‌صورت خودکار ایجاد کن.
  - آزمون/معیار موفقیت: اجرای برنامه در مسیر فاقد پایگاه داده فایل و جداول را بسازد و API قابل استفاده باشد.
- [x] جداسازی داده‌ها بر اساس کاربر را در مدل و مسیرهای API رعایت کن.
  - آزمون/معیار موفقیت: آزمون‌ها نشان دهند داده هر کاربر به برد همان کاربر محدود است و هر کاربر فقط یک برد دارد.
- [x] آزمون‌های واحد بک‌اند را برای خواندن، ایجاد و تغییر داده و خطاهای ورودی اضافه کن.
  - آزمون/معیار موفقیت: آزمون‌ها با پایگاه داده آزمایشی اجرا شوند و حالت‌های موفق و نامعتبر را پوشش دهند.
  - نتیجهٔ اجرا: هر ۶ آزمون در کانتینر و با وابستگی‌های بخش `dev` در `backend/pyproject.toml` موفق شدند.

## بخش هفتم: اتصال فرانت‌اند و بک‌اند

- [x] فرانت‌اند را به API متصل کن و داده برد را از بک‌اند بخوان و تغییرها را از طریق API ذخیره کن.
  - آزمون/معیار موفقیت: برد نمایش‌داده‌شده از API دریافت شود و ویرایش کارت، جابه‌جایی کارت و تغییر نام ستون به API برسد.
- [x] داده را در SQLite نگه دار و آن را در volume محلی Docker پایدار کن.
  - آزمون/معیار موفقیت: پس از بارگذاری مجدد صفحه و راه‌اندازی مجدد یا ساخت مجدد کانتینر با همان volume، تغییرهای ذخیره‌شده باقی بمانند.
- [x] مسیرهای اصلی را به‌صورت یکپارچه از مرورگر تا پایگاه داده آزمایش کن.
  - آزمون/معیار موفقیت: آزمون یکپارچه‌سازی خواندن، تغییر، ذخیره و بازیابی دوباره برد را تأیید کند.
  - نتیجهٔ اجرا: ۲۴ آزمون فرانت‌اند، ۱۱ آزمون مرورگر، lint و build موفق شدند. آزمون مرورگر ماندگاری پس از بارگذاری مجدد را تأیید کرد و یک کارت آزمایشی پس از راه‌اندازی مجدد کانتینر با همان volume باقی ماند؛ سپس کارت آزمایشی حذف و برد به حالت اولیه بازگردانده شد.

## بخش هشتم: اتصال به OpenRouter

- [x] درخواست بک‌اند به OpenRouter را با مدل `openai/gpt-oss-120b` پیاده‌سازی کن و کلید را از `OPENROUTER_API_KEY` در `.env` ریشه بخوان.
  - آزمون/معیار موفقیت: کلید در کد یا پاسخ API افشا نشود و درخواست با مدل تعیین‌شده ارسال شود.
- [x] اتصال زنده را با درخواست ساده `2+2` بررسی کن.
  - آزمون/معیار موفقیت: در محیط دارای کلید معتبر، پاسخ مدل نتیجه `4` را تأیید کند؛ خطای نبود کلید یا خطای سرویس به‌صورت روشن گزارش شود.
  - نتیجهٔ اجرا: ۱۳ آزمون بک‌اند موفق شدند. درخواست زنده با مدل رایگان `liquid/lfm-3-1.7b:free` پاسخ `4` داد. مدل پیش‌فرض همچنان `openai/gpt-oss-120b` است؛ برای آزمایش رایگان، `OPENROUTER_MODEL` را با شناسهٔ مدل تنظیم کنید.

## بخش نهم: گفت‌وگوی ساختاریافته با هوش مصنوعی

- [ ] اطلاعات کامل برد، پرسش جاری کاربر و تاریخچه مکالمه را در درخواست مدل بگنجان.
  - آزمون/معیار موفقیت: آزمون درخواست ارسالی را بررسی کند و وجود هر سه ورودی را تأیید کند.
- [ ] خروجی ساختاریافته تعریف کن که پاسخ متنی به کاربر و به‌روزرسانی اختیاری برد را ارائه دهد.
  - آزمون/معیار موفقیت: پاسخ معتبر با و بدون به‌روزرسانی پذیرفته شود؛ خروجی نامعتبر به‌عنوان خطا گزارش شود و برد را تغییر ندهد.
- [ ] پیشنهادهای تغییر برد را بدون اعمال خودکار برگردان تا کاربر بتواند آن‌ها را بررسی و تأیید کند.
  - آزمون/معیار موفقیت: تا پیش از تأیید کاربر، داده ذخیره‌شده تغییر نکند.
- [ ] آزمون‌های بک‌اند را برای ورودی‌ها، شکل خروجی، تاریخچه، پیشنهاد تغییر و خطاهای مدل اضافه کن.
  - آزمون/معیار موفقیت: آزمون‌های مستقل از سرویس زنده، حالت‌های اصلی و نامعتبر را پوشش دهند؛ اتصال واقعی نیز با کلید معتبر بررسی شود.

## بخش دهم: دستیار هوش مصنوعی در رابط کاربری

- [ ] ابزارک گفت‌وگو را در نوار کناری اضافه کن.
  - آزمون/معیار موفقیت: کاربر بتواند پیام بفرستد، پاسخ را ببیند و تاریخچه مکالمه را در طول گفت‌وگو حفظ کند.
- [ ] پاسخ و پیشنهاد تغییر برد را نمایش بده و پیش از اعمال پیشنهاد، تأیید صریح کاربر بگیر.
  - آزمون/معیار موفقیت: رد پیشنهاد هیچ تغییری ایجاد نکند؛ تأیید پیشنهاد آن را از طریق API اعمال کند.
- [ ] پس از اعمال موفق تغییر پیشنهادی، برد را از داده به‌روز‌شده تازه‌سازی کن.
  - آزمون/معیار موفقیت: ستون یا کارت تغییر‌یافته بدون بارگذاری دستی صفحه به‌روز نمایش داده شود و پس از بارگذاری مجدد نیز باقی بماند.
- [ ] آزمون‌های انتها‌به‌انتها را برای گفت‌وگو، تأیید/رد تغییر و به‌روزرسانی برد اجرا کن.
  - آزمون/معیار موفقیت: مسیر کامل از ارسال پیام تا نمایش پیشنهاد، تأیید کاربر، ذخیره تغییر و تازه‌سازی رابط با موفقیت طی شود.

## بخش یازدهم: بومی‌سازی و بازطراحی رابط

- [x] رابط را به فارسی و انگلیسی ارائه کن و جهت صفحه و اجزای برد را متناسب با زبان تغییر بده.
  - آزمون/معیار موفقیت: متن‌های رابط و شش نام پیش‌فرض ستون‌ها ترجمه شوند؛ فارسی راست‌چین و انگلیسی چپ‌چین باشد؛ متن کارت‌ها و نام‌های سفارشی ستون‌ها دست‌نخورده بمانند.
- [x] کلید تغییر زبان و حالت روشن/تاریک را اضافه کن و انتخاب‌ها را در `localStorage` نگه دار.
  - آزمون/معیار موفقیت: تغییر زبان و پوسته بدون بارگذاری مجدد اعمال شود و پس از بارگذاری مجدد حفظ شود.
- [x] پالت سرمه‌ای/آبی تیره و کرم نود با نارنجی پرتقالی روشن در پوستهٔ روشن و آبی آسمانی نئونی در پوستهٔ تاریک اعمال کن؛ دکمهٔ ورود و سربرگ نمای کلی کارها را هم‌رنگ کن و رنگ‌های پاستیلی ستون‌ها را حفظ کن.
  - آزمون/معیار موفقیت: هر دو پوسته خوانا باشند، رنگ پاستیلی ستون‌ها حفظ شود و نوار افقی جابه‌جایی برد در هر دو پوسته واضح باشد.
- [x] جابه‌جایی کارت‌ها را نرم‌تر کن و تنظیم حرکت کمینهٔ سیستم‌عامل را حفظ کن.
  - آزمون/معیار موفقیت: جابه‌جایی و مرتب‌سازی کارت‌ها و ستون‌ها در آزمون مرورگر موفق باشد؛ برای `prefers-reduced-motion` حرکت اضافی اعمال نشود.
  - نتیجهٔ اجرا: ۲۶ آزمون فرانت‌اند، ۱۲ آزمون مرورگر، lint و build موفق شدند. آزمون مرورگر روی سرویس کامل محلی اجرا شد و تغییر/ماندگاری زبان و پوسته، جهت صفحه و تعامل‌های موجود را تأیید کرد؛ پوستهٔ روشن/تاریک و چیدمان دو‌زبانه نیز در مرورگر بررسی بصری شدند.
